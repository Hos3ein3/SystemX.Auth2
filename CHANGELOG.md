# Changelog

All notable changes are listed here. The format follows "Keep a Changelog".

## [Unreleased]

### Fixed
- **Scope rules never passed for a hosted-UI cookie user.** The identity token has no `scope` claim, so the cookie had none and `ICurrentClient.Scopes`, `[Auth2Scope]` and `WithScope` refused everybody. The same for `ICurrentClient.ClientId`, `ApplicationId`, `ProjectId`, `ProjectKey` and `SessionId`. The scopes and these facts of the access token are copied into the cookie at sign-in now.
- **The demo data was added to `_global` instead of the sample project.** The project of a scope of the services stays the one that was asked for first, and the seed of the admin asks for `_global`. The demo seed now runs in its own scope, and an install that already has the demo data in `_global` is repaired at the next seed (the misplaced demo people, roles, groups and permissions are removed from `_global` and added to `sample-project`).
- **The token endpoint did not follow the language.** `error_description` of a failed sign-in was the error code with spaces; it is now written in the language of the call like the messages of the JSON API (`error`, `error_code` and the status code are unchanged).
- **Client: the texts on `[Auth2Permission]`, `[Auth2Role]`, `[Auth2Scope]` and `[Auth2Group]` were ignored by the scan** when the attribute sat on an endpoint, class or method (only constants were read). `DisplayName`, `Description`, `Group` and a role's `Permissions` now reach the catalog when the attribute names exactly one key. See [docs/client-endpoint-metadata.md](docs/client-endpoint-metadata.md).
- **Client: a session that ended on the server no longer throws.** After a sign-out on the Auth2 server the application still had its own cookie, and the next `ICurrentUser.GetRolesAsync()` (or permissions) failed with an unhandled `Auth2Exception` (`invalid_token`). `UseAuth2()` now adds a small middleware: it removes the cookie and sends a browser to sign in again; an API call gets 401. Other errors are still thrown.
- **Server home page (`/`) threw `ProjectNotFoundException`** for a signed-in user who is not a global admin. It looked up roles with `UserManager` while no project was selected; the roles are already claims of the session, so the lookup is gone. The redirect to the user's own project also read the wrong claim name (`project_key` instead of `projectkey`).

### Added
- **`PublicUrl` of the two-way health check is optional.** Without it the client tells the Server only its port, scheme and path (`ClientHandshakeRequest.HealthPort`, `HealthScheme`, `HealthPath`; found in `urls`, `ASPNETCORE_URLS`, `http_ports` or the web server addresses) and the Server calls `http://{network address of the handshake}:{port}{path}`. With `PublicUrl` the Server calls exactly that. Both samples and docker-compose no longer set it.
- **Refresh buttons** next to the `Clients`, `PostgreSQL` and `Redis` badges of the project dashboard: the `Clients` one asks this project's two-way clients now (`IClientHealthService.CheckProjectAsync`).
- **PostgreSQL and Redis on the project dashboard.** The server's two health checks (`database`, `redis`) are shown to global admins as badges (`PostgreSQL: Healthy`, `Redis: Healthy` or `Redis: Off`) beside `Jobs` and `Status` on `/admin/p/{project-key}`. See [docs/observability.md](docs/observability.md#health-checks).
- **A complete guide to scopes.** `docs/scopes.md` explains the standard, `auth2.*` and custom scopes, how a scope gets into a token, how to create, allow, ask for and check one, and the resources of a scope (the page that was `scope-resources.md` is part of it now).
- **Two-way health check.** `EnableHealthCheck(o => o.Mode = Auth2HealthCheckMode.TwoWay)` (with `PublicUrl` and an optional `Path`, default `/auth2/health`): the client also answers the Server's question "are you healthy and ready?" with the result of all its health checks, the handshake tells the Server where (`ClientHandshakeRequest.HealthUrl`), and the Server asks every minute (`Auth2:Jobs:ClientHealthEnabled`, `ClientHealthIntervalSeconds`, `ClientHealthTimeoutSeconds`) and shows `Clients: Healthy` (or `n of m not healthy`) on the project dashboard (`/admin/p/{project-key}`) beside `Jobs` and `Status`. One-way stays the default. Both samples use two-way. See [docs/client-health-check.md](docs/client-health-check.md).
- **MVC sample: a showcase of every rule.** `HomeController` has one action for each kind of rule (permissions any / all / only from a role / only granted, roles, groups, scopes, scope AND permission, the "any of" family, the audit hook), a **Rules** page that lists them and an **Inspect** page that shows the checks in code and the audiences of the token. The sample scopes now have resources (`reports-api`, `orders-api`). See [docs/sample-mvc.md](docs/sample-mvc.md).
- **Scope resources are applied.** The "Associated Resources" of a scope now become audiences (`aud`) of the access tokens that have the scope (user tokens, machine tokens, and after a refresh): the client id of the application stays first, then the resources of the granted scopes. An API can accept only tokens made for it with `UseApiAuthentication(o => o.Audience = "orders-api")`. The Server finds the application of a token from the `client_id` claim (`TokenAudience`), so a resource that is another application's client id selects nothing. See [docs/scopes.md](docs/scopes.md).
- **Demo data for the samples:** when `Auth2:SeedDemoData` is `true` (default `false`; on in `appsettings.Development.json` and `docker-compose.yml`) the seeder adds demo data to `sample-project`: 60 permissions, 55 roles, 53 groups, 60 scopes (allowed for both sample applications) and 56 people (password `Demo@12345!`), with roles, groups and direct permissions assigned, so the MVC and Minimal API samples can be tried at once. The demo seed runs after the main seed is committed and cannot stop the server from starting. See [docs/seeding.md](docs/seeding.md#demo-people-for-the-samples-development-only).
- **Privacy and Terms pages** (`/Privacy`, `/Terms`): public pages with English text for an open-source, self-hosted server (data kept, cookies, recipients, user choices, MIT licence, terms of use), with a note for operators. They show the project's brand name and support address when the application is known, and the footer of the sign-in layout links to them. See [docs/ui-handover.md](docs/ui-handover.md#privacy-and-terms-pages).
- **"Any of" authorization rules** (OR across kinds): `WithAnyOf`, `WithRoleOrPermission`, `WithRoleOrGroup`, `WithPermissionOrGroup`, `WithScopeOrRole` for Minimal API and the attributes `Auth2AnyOf`, `Auth2RoleOrPermission`, `Auth2RoleOrGroup`, `Auth2PermissionOrGroup`, `Auth2ScopeOrRole`. The scanners read the roles, permissions, groups and scopes of these rules, so they are synced. See [docs/client-endpoint-metadata.md](docs/client-endpoint-metadata.md#any-of-rules-a-role-or-a-permission).
- **`IAuth2ApiClientService` has the methods of every account route:** `ConfirmEmailAsync`, `ResendEmailConfirmationAsync`, `ConfirmPhoneAsync`, `CompleteJoinAsync`, `SetupTwoFactorAsync`, `EnableTwoFactorAsync`, `DisableTwoFactorAsync`, `RegenerateRecoveryCodesAsync`, and the new `ChangeUserNameAsync`, `RequestEmailChangeAsync`, `ConfirmEmailChangeAsync`, `RequestPhoneChangeAsync`, `ConfirmPhoneChangeAsync`. See [docs/client-api-service.md](docs/client-api-service.md).
- **New JSON routes** (user token, scope `auth2.me`): `POST /api/auth2/user-name/change`, `/email/change`, `/email/change/confirm`, `/phone/change`, `/phone/change/confirm`. The pages of `/Account` and the routes share one service (`IAccountChangeService`).
- **Language of the calls.** Every Client call sends `Accept-Language` (the current request's culture; `Auth2ClientOptions.SendRequestCulture`, on by default), and `IAuth2ApiClientService.WithCulture("fa")` chooses another, so messages, emails and SMS are in the user's language.
- **Pages to change the own account details** in `Pages/Account`: `ChangePassword`, `ChangeUserName`, `ChangeEmailAddress`, `ChangePhoneNumber` (page models only; the HTML is not drawn yet). The new email address gets a confirmation link and the new phone number an SMS code before anything changes. A person with a password gives it again. Audit events `user.name_changed`, `email.change_requested`, `email.changed`, `phone.change_requested`, `phone.changed`. New OTP purpose `change_phone`; new email and SMS texts `change_email.*` and `sms.change_phone` (English and Persian). See [docs/ui-handover.md](docs/ui-handover.md#account-change-pages-signed-in).
- **Setting `Password.SignOutAfterChangePassword`** (GlobalOnly, off by default): after a password change by the person, every session ends, also the one that made the change. It applies to the page and to the API route `/password/change`.
- **Docs:** [access-concepts.md](docs/access-concepts.md) (scope, permission, role, group, direct grant, token kind: which is which) and [client-endpoint-metadata.md](docs/client-endpoint-metadata.md) (Minimal API methods and attributes, when to use which, what the scanners read).
- **Password history and expiry.** New table `password_history` (hashes of replaced passwords) and four password settings (GlobalOnly, all off by default): `SaveOldPasswords`, `OldPasswordsToKeep` (1 to 24, default 5), `AllowOldPasswordReuse` and `PasswordExpiryDays`. With the history on, the current password is refused as a new one, and with reuse off so is every remembered one (with reuse on only the one right before). An expired password answers `password_expired` at the password sign-in until it is reset. New error codes `password_reused` and `password_expired`; new column `password_changed_at_utc` on `users` and `user_projects`. One additive migration (`PasswordHistory`). See [docs/password-history.md](docs/password-history.md).
- **Docs:** [redis.md](docs/redis.md) (what Redis holds, how to enable it, what happens when it is down, the Client's access-data cache in Redis or memory).
- **`Registration.AssignedRoles`, `AssignedGroups`, `AssignedPermissions`** (GlobalOnly). A new member gets them when registering, when joining a project with proof of ownership, and at the first external sign-in. Missing names are skipped and audited (`register.defaults_applied`); the built-in admin roles are refused. See [ADR-098](docs/decisions.md) and [server-settings.md](docs/server-settings.md).
- **Setting `Registration.SendConfirmationEmail`** (default on; an application can override it). When off, registration does not send the confirmation email; it is still sent when `Email.RequireConfirmedEmail` is on, and the resend route works either way.
- **EmailFactory and SmsFactory.** The default `IEmailSender` / `ISmsSender` ask `IEmailFactory` / `ISmsFactory`, which pick the provider per request: the application's, else the project's, else the server default (`Auth2:Messaging`), else logging. New providers: `smtp` (MailKit) and `google` (Gmail, app password). Add your own with `IEmailTransport` / `ISmsTransport`. Settings are `GlobalOnly` and live in `ProjectSettings.Messaging` and `ClientApplicationSettings.Messaging`; the password is encrypted and never returned. Admin routes: `GET|PUT /projects/{id}/messaging`, `GET|PUT|DELETE /projects/{id}/applications/{appId}/messaging`. See [docs/email-and-sms.md](docs/email-and-sms.md).

### Changed
- **Social login and generic OpenID Connect now use OpenIddict.Client** (`OpenIddict.Client.AspNetCore`, `.SystemNetHttp`, `.WebIntegration`) instead of a hand-written client. Registrations are built from the provider list at run time (no restart); see ADR-096 for the spike result and the findings. Behaviour changes: a specific Microsoft tenant refuses another tenant at the issuer check; Apple, Google and GitHub follow the library (RFC 9207 `iss`); the Facebook Graph version is applied to the library's endpoints. Upstream tokens are never stored in the Server's token table.
- The HTTP clients of OpenIddict.Client get the SSRF guard (`SsrfGuardHandler`). The answer of a provider (`/callback/login/...`) is read by Auth2 itself; the OpenIddict middleware does not handle it.

### Changed (breaking, pre-1.0)
- **Project vs Application.** The old "application" (tenant + client) is split. **Project** = the tenant (table `projects`, `ProjectKey` never changes, project settings). **Application** = a client of a project and **is** the OpenIddict application table (`applications`, custom OpenIddict entities with `ProjectId`, `IsEnabled`, `Name` unique inside the project, `SettingsJson`), created, changed and deleted only through `IOpenIddictApplicationManager`.
  `user_applications` is now `user_projects`; every tenant table uses `ProjectId` (the query filter too). Audit events, sessions and synced catalog items keep an **optional** `ApplicationId`. One data-preserving migration (`ProjectsAndApplications`, hand-written, upgrade test compares the result with a fresh schema). OpenIddict major upgrades need a migration review.
  Access rule: a member of a project can use every application of it. Joining is a project setting.
  Enabled/disabled: one shared gate (`AccessGate`) for every sign-in path and token (OpenIddict event handlers for validation); generic public answer `access_denied`, the reason only in the audit log; disabling a project revokes tokens, authorizations and sessions in one transaction; a short cached status (`Auth2:ProjectStatusCacheSeconds`).
  `ServerWithSingleApplication()` is now `ServerWithSingleProject()`, `IApplicationContext` is `IProjectContext`, new `IClientApplicationContext`; claims are `project_id`, `projectkey`, `client_id`, `application_id` (the `app` claim is gone); the login cookie is per project (`.SystemX.Auth2.Session.{projectkey}`).
  Two-level settings with one resolver (`EffectiveSettings`): project default, overridden by the application value. Handshake request: `ProjectKey` (multi mode only) + `ApplicationName`; the answer returns `ProjectId` and `ApplicationId`; a key sent to a single-project server is ignored with a warning.
  Admin API: `/projects`, `/projects/{projectId}/users|roles|permissions|groups|settings|audit-events|external-*`, `/projects/{projectId}/applications/{applicationId}/...` (client setup page data, secret shown once). Commands: `create-project`, `create-application`, `rotate-client-secret <clientId>`.
- **`ICurrentClient` and `ICurrentUser` are split.** `ICurrentClient`: token, client id, application id, project id and key, scopes, `HasScope`, machine flag, session id, `Idp`, `Amr` (synchronous, from claims). `ICurrentUser`: the person only (`IsAuthenticated` is false for machine tokens).
- **Catalog sources.** One generic `CatalogOptions<T>` for permissions, roles, scopes and groups with `Add`, `AddFromClass`, `AddFromEnum`, `AddFromString`, `AddFromListString`, `AddProvider`, `AddFactory`, `AddFromConfiguration`; merge by key, `DuplicatePolicy`, startup validation that names the source; `[Auth2Key]`, `[Auth2Category]`, attributes usable on fields.
