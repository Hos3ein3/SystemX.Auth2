# Changelog

All notable changes are listed here. The format follows "Keep a Changelog".

## [Unreleased]

### Added
- **`WithTotp()` / `[Auth2Totp]` in the hosted UI: the Server asks for the code.** A browser request without a fresh proof is sent to `/connect/authorize` with `acr_values=urn:systemx:auth2:acr:totp` (new `Auth2AcrValues.Totp`); the Server shows `/Account/VerifyTotp` (or, for a person without two-factor, the page that tells how to turn it on), goes on with the sign-in, and the access token carries the new claim `step_up_at` (`Auth2Claims.StepUpAt`). The tokens also carry `step_up_until` (`Auth2Claims.StepUpUntil`), written from the project setting **`TwoFactor.StepUpMinutes`**; the Client lets the request pass until then and has no window of its own (one source of truth). APIs and the Self UI are unchanged (a code in `X-Auth2-Totp` / `auth2_totp`). A cookie (`.SystemX.Auth2.StepUp`) stops endless round trips. A silent `prompt=none` request gets `interaction_required`. The "back" link of the page leaves out the step-up value. Samples: `SecureArea`, `TransferForm` and `Transfer` in the MVC sample, `POST /api/transfers` (`WithTotp()`) and `POST /api/notes` (`WithOptionalTotp()`) in the Minimal API sample. See [docs/client-endpoint-metadata.md](docs/client-endpoint-metadata.md#hosted-ui-the-server-asks-for-the-code-on-its-own-page).
- **Client: `ICurrentUser` knows more.** New `HasGroupAsync(group)`, `IsEmailAddressConfirmed` and `IsPhoneNumberConfirmed`. The Server puts the standard claim `phone_number_verified` (and, on refresh, `email_verified`) in the token with the `phone` and `email` scopes, like the values themselves; the cookie sign-in copies them. See [docs/client-current-user.md](docs/client-current-user.md).
- **Client: manage people, roles, permissions, groups and scopes.** `IAuth2ApiClientService.Admin` and `IAuth2WebClientService.Admin` (the same type, `IAuth2AdminClientService`; the web one takes the token from the cookie) create, read, change and delete, grouped by what they work on: `Admin.Users`, `Admin.Roles`, `Admin.Permissions`, `Admin.Groups`, `Admin.Scopes` (for example `Admin.Roles.AddPermissionAsync`, `Admin.Groups.AddMemberAsync`, `Admin.Users.AssignRoleAsync`). `Admin.Users` has create, read, change, delete, lock and unlock, reset two-factor, sessions, and the roles, permissions and groups of a person. They call the admin API with the token of a signed-in admin that has the scope `auth2.admin`; the token of the application is refused. `Admin.ForProject(id)` is for a GlobalAdmin. New contracts `PageRequest` and `Auth2AdminRoutes` (every admin route as a constant, used by the Server endpoints and by the Client). See [docs/client-api-service.md](docs/client-api-service.md#people-roles-permissions-groups-and-scopes-the-admin-calls).
- **Admin API: change and read one.** `PUT /roles/{id}` (description; a role is never renamed; system, `GlobalAdmin`, `Developer` and global roles are refused), `PUT /permissions/{id}` (display name, description, group), `PUT /groups/{id}`, `GET /roles/{id}`, `/permissions/{id}`, `/groups/{id}`, and the new scope routes `GET`, `POST`, `PUT`, `DELETE /projects/{projectId}/scopes[/{id}]` (read by every admin, changed by a GlobalAdmin). `POST /roles`, `/permissions` and `/groups` now answer with the new item and its `id`. New `IAccessService.UpdateRoleAsync`, `UpdatePermissionAsync` and `IGroupService.UpdateAsync` (audited as `role.updated`, `permission.updated`, `group.updated`). See [docs/admin-api.md](docs/admin-api.md#roles-permissions-groups).

### Fixed
- **After the second step of the sign-in, an ordinary person landed on a "not found" page.** The home page (`/`) sent every signed-in person who is not a global admin to `/admin/p/{project}`, and the admin pages answer 404 to anyone who is not a project admin. Only a project admin goes there now; everybody else goes to `/Manage/Profile`. It happened with an authenticator code and with a recovery code alike.
- **The code boxes of `/Account/TwoFactor`, the 2FA setup and recovery-codes pages, `ConfirmPhone` and `VerifyOtp` took letters and any length.** They now carry the same digits-only rule as `VerifyTotp` (`inputmode="numeric"`, `pattern`, `maxlength="10"`, `data-a2-digits`). The recovery-code boxes still take any text.
- **Saving the project settings page put the branding back to the defaults.** `/admin/p/{key}/settings` has no fields for the parts that have their own pages, so the first save replaced the colours of the branding, the messaging (email and SMS provider) and the external providers with the defaults. The page now keeps what is saved for those parts. Test: `SavingTheSettingsPage_KeepsWhatHasItsOwnPages_BrandingAndMessagingAndProviders`.
- **`/Account/VerifyTotp`: the error was shown twice, and the code box took letters.** `_LayoutAuth` already shows the error of the page; six pages (verify code, change user name, email, password, phone, reset password, join project) showed it a second time in the form and no longer do. The code box takes digits and spaces only (`inputmode`, `pattern`, `maxlength`, and `data-a2-digits` which `a2.js` uses to drop other characters, typed or pasted).
- **A form of a sign-in page could hang in Chromium browsers when the redirect after it ended at the application.** The page policy said `form-action 'self'`, and a browser checks the whole redirect chain of a form against it (the code on `/Account/VerifyTotp` → `/connect/authorize` → the `redirect_uri` of the application): the last step was blocked and the page kept its loading screen. The origins of the registered redirect addresses of the application are now named in `form-action` of those pages (exact origins, nothing else).
- **The user name is the identity at sign-in.** A person whose user name looks like an email address or a phone number (set with the change-user-name page, an admin, or an import) could not sign in with it: the text was looked up only in the email or phone column. Now the exact user name is tried first, whatever it looks like, then the email, then the phone number. The method that found the person must be allowed (`UserNamePassword` for a user name, `EmailPassword`, `PhonePassword`); the answers for a method that is not allowed are the same as before. The same lookup serves register, forgot password, confirm, join and the passkey sign-in. New rule in `Auth2UserValidator`: **one text never names two people**: a person's email or phone number cannot be the user name of somebody else, and a user name cannot be another person's email or phone number (`DuplicateEmail`, `DuplicateUserName`, the new `phone_number_taken`, localized in all seven languages). A person may use their own email or phone number as their user name. Data that already breaks the rule is not changed. See [docs/authentication-flows.md](docs/authentication-flows.md#how-a-person-is-found-at-sign-in).
- **Sign-in and sign-up pages had fixed inputs and no early validation.** The login input was always "Username or email" (even when only phone sign-in was allowed), the placeholder was an email address, and the password, user name, email and phone rules saved in the project settings were only checked after the click. The pages now draw the identifier input from `Methods.AllowedLoginMethods` / `AllowedRegisterMethods` (label, type, keyboard, `autocomplete`; required only when it is the only way) and give the browser the saved rules (`data-a2-rule`, read by `wwwroot/js/a2.js`): messages in the page language under the input while the person types, a live password requirements list, "repeat password" matching, and a blocked submit with the first message. The same for forgot password, join, reset password, change password, change user name, change email and change phone. The wrong hint "At least 12 characters recommended" is gone. The Server still checks everything on submit. See [docs/ui-handover.md](docs/ui-handover.md#inputs-and-rules-come-from-the-project-settings).
- **Scope rules never passed for a hosted-UI cookie user.** The identity token has no `scope` claim, so the cookie had none and `ICurrentClient.Scopes`, `[Auth2Scope]` and `WithScope` refused everybody. The same for `ICurrentClient.ClientId`, `ApplicationId`, `ProjectId`, `ProjectKey` and `SessionId`. The scopes and these facts of the access token are copied into the cookie at sign-in now.
- **The demo data was added to `_global` instead of the sample project.** The project of a scope of the services stays the one that was asked for first, and the seed of the admin asks for `_global`. The demo seed now runs in its own scope, and an install that already has the demo data in `_global` is repaired at the next seed (the misplaced demo people, roles, groups and permissions are removed from `_global` and added to `sample-project`).
- **The token endpoint did not follow the language.** `error_description` of a failed sign-in was the error code with spaces; it is now written in the language of the call like the messages of the JSON API (`error`, `error_code` and the status code are unchanged).
- **Client: the texts on `[Auth2Permission]`, `[Auth2Role]`, `[Auth2Scope]` and `[Auth2Group]` were ignored by the scan** when the attribute sat on an endpoint, class or method (only constants were read). `DisplayName`, `Description`, `Group` and a role's `Permissions` now reach the catalog when the attribute names exactly one key. See [docs/client-endpoint-metadata.md](docs/client-endpoint-metadata.md).
- **Client: a session that ended on the server no longer throws.** After a sign-out on the Auth2 server the application still had its own cookie, and the next `ICurrentUser.GetRolesAsync()` (or permissions) failed with an unhandled `Auth2Exception` (`invalid_token`). `UseAuth2()` now adds a small middleware: it removes the cookie and sends a browser to sign in again; an API call gets 401. Other errors are still thrown.
- **Server home page (`/`) threw `ProjectNotFoundException`** for a signed-in user who is not a global admin. It looked up roles with `UserManager` while no project was selected; the roles are already claims of the session, so the lookup is gone. The redirect to the user's own project also read the wrong claim name (`project_key` instead of `projectkey`).

### Changed
- **BREAKING (Client): `IAuth2WebService` is now `IAuth2WebClientService`, in `SystemX.Auth2.Client.Services`** (it was in `SystemX.Auth2.Client.Authentication`), next to `IAuth2ApiClientService`. The implementation class is `Auth2WebClientService`. Only the name and the namespace changed: add `using SystemX.Auth2.Client.Services;` and rename the type.
- **BREAKING (Client): no `HttpContext` and no tokens in the method calls.** `IAuth2WebClientService` no longer takes an `HttpContext`: they use the current request (`IHttpContextAccessor`) and throw `InvalidOperationException` when there is none (for example in a background job; use `IAuth2ApiClientService` there). `IAuth2ApiClientService` and the admin calls no longer take an access token or a refresh token: the calls that act for a person use the access token of the current request (`IAuth2AccessTokenAccessor`: the bearer header, or the token that the cookie sign-in saved), and `RefreshAsync()` / `LogoutAsync()` use the refresh token of the cookie (new `IAuth2AccessTokenAccessor.GetRefreshTokenAsync`). Where there is no request, or you hold the tokens yourself, choose them with the new `IAuth2ApiClientService.WithTokens(accessToken, refreshToken)` (a copy, like `WithCulture`). With no token the answer is `invalid_token`. Change `api.GetMeAsync(token)` to `api.GetMeAsync()` (or `api.WithTokens(token).GetMeAsync()`), `web.LoginAsync(http, request)` to `web.LoginAsync(request)`, and so on. See [docs/client-api-service.md](docs/client-api-service.md).
- **No route strings in the endpoints.** The routes of the admin API are constants in the new `Auth2AdminRoutes` (Contracts; templates such as `Role = "/roles/{id:guid}"`, with `Fill` and `ForProject` for callers), and the passkey, external sign-in and branding routes are constants in `Auth2Routes`. The Server endpoints and the Client's `Auth2AccessApi` use them, so the two sides cannot disagree. The routes themselves did not change; `ExternalEndpoints.Providers` and `Challenge` moved to `Auth2Routes.ExternalProviderList` and `ExternalChallenge`.
- **Settings stay in the cache for 1 day (was 10 minutes).** Project settings change rarely, and a change clears the cache at once (version raised in Redis). Without Redis, other instances see a change only when their copy expires, so use Redis with more than one instance. See [docs/redis.md](docs/redis.md#the-hybrid-cache-settings-without-asking-the-database).
- **The self-service pages (`/Manage`) look like the admin console.** `_LayoutAccount` was rebuilt on the design of the admin layout (sidebar with the same active-link style, header with the language selector and the dark-mode button, mobile navigation, a way back to the admin console for admins) and the ten pages got dark-mode classes. The password and email forms use the saved project rules in the browser. The admin console has a new sidebar section **My account** with all the pages (the links carry the client id of the session cookie). See [docs/ui-handover.md](docs/ui-handover.md#the-self-service-pages-manage).
- **Settings come from a hybrid cache (memory + Redis), checked by version.** New `IHybridCacheService` / `HybridCacheService` (registered by `AddAuth2Caching()`). `ProjectSettingsProvider` no longer reads PostgreSQL every 10 minutes on every instance: a read asks Redis only for a small version number and uses the copy in memory when it is the same; a changed version loads the value from Redis, and only when Redis has none for the current version is the database read (once, for all instances). A settings change raises the version, so every instance sees it on its next read. A value read before a change is never stored after it (Lua script). Without Redis it is the memory of the instance as before; when Redis fails the cache keeps working from memory and the database. See [docs/redis.md](docs/redis.md#the-hybrid-cache-settings-without-asking-the-database).
- **The project and the calling application are cached too** (`AuthFlowCache`). `IProjectContext` and `IClientApplicationContext` (what `Auth2PageModel` and `IAuthFlowResolver` read first on every request: project, settings, application) no longer query PostgreSQL on every request: the project row, the application row and the id a project key, client id or single-project name belongs to are in the hybrid cache and checked by version. Every write path drops them: saving settings, renaming, enabling, disabling or deleting a project, creating, changing or deleting an application, a handshake that changes the web server address or type, the project settings changing the consent type of its applications, and the seed (which also clears Redis copies that outlive a restart). Provider secrets inside the settings are stored in Redis in their encrypted form.
- **`CatalogRefreshInterval` is checked at start.** It must be from 30 seconds to 40 days, or `Timeout.InfiniteTimeSpan` to read the catalogs only once at start. A value of `0` used to make the application ask the Server again and again; now it stops the application with a clear message.

### Added
- **A project name is unique.** The name of a project cannot be the name of another project, compared without letter case and without spaces around (`Shop`, `shop` and ` SHOP ` are the same). The admin API and pages answer `project_name_taken` (`409`, localized in all seven languages) on create and on rename (a project may keep its own name or change only its letters); `IProjectService.CreateAsync` throws `ProjectNameTakenException`. The database enforces it too (unique index `ux_projects_name_ci` on `lower(btrim(name))`, migration `UniqueProjectName`), so two requests at the same moment cannot both win. The migration first renames old duplicates (the oldest keeps its name, the others become `Name (2)`...). The seed never fails because of a name: if a person already used `Global` or `Sample Project` for another project, the seeded project becomes `Sample Project (sample-project)`.
- **Razor runtime compilation in development.** `AddRazorRuntimeCompilation` is on in the `Development` environment (or with `Auth2:RazorRuntimeCompilation=true`; `false` turns it off): a change of a `.cshtml` file shows after a refresh, without a build. Not for production. New package `Microsoft.AspNetCore.Mvc.Razor.RuntimeCompilation`. See [docs/contributing-workflow.md](docs/contributing-workflow.md#editing-pages-without-a-rebuild).
- **`IAuth2WebClientService` has the account calls of `IAuth2ApiClientService`, for websites with their own forms (Self UI).** New methods: `RegisterAsync`, `RequestOtpAsync`, `ForgotPasswordAsync`, `ResetPasswordAsync`, `ConfirmEmailAsync`, `ResendEmailConfirmationAsync`, `ConfirmPhoneAsync`, `CompleteJoinAsync`, `GetExternalProvidersAsync` (people who are not signed in), and, taking the `HttpContext` and using the **access token of the session cookie**: `GetMeAsync`, `RefreshAsync`, `ChangePasswordAsync`, `ChangeUserNameAsync`, `RequestEmailChangeAsync`, `ConfirmEmailChangeAsync`, `RequestPhoneChangeAsync`, `ConfirmPhoneChangeAsync`, `SetupTwoFactorAsync`, `EnableTwoFactorAsync`, `VerifyTotpAsync`, `DisableTwoFactorAsync`, `RegenerateRecoveryCodesAsync`. The application never handles a token: when the access token is old the call is refused with `invalid_token`, the service refreshes it once, saves the new tokens in the cookie and asks again; requests that refresh at the same moment share one refresh (a refresh token works once). See [docs/client-api-service.md](docs/client-api-service.md#iauth2webservice-or-iauth2apiclientservice).
- **Sudo mode for restricted pages of the Server, like GitHub.** A person who has two-factor on is asked for a code of the authenticator app **again** before `/Manage/DeleteAccount` and before turning two-factor off, unless they gave one in this session within `TwoFactor.StepUpMinutes` (new project setting, default 15, `0` = off, global admin only, a field in the settings page). The restricted page redirects to `/Account/VerifyTotp` and comes back; the second step of the sign-in counts as a code; the time is a claim of the session cookie (`step_up_at`), so another browser is asked on its own, and pages that sign the session in again keep it. `ManagePageModel.RequireRecentTotpAsync()` protects one more page. [docs/two-factor.md](docs/two-factor.md#the-pages-and-what-each-one-is-for) now also explains which page does what (`/Account/TwoFactor` is the second step of the sign-in, `/Account/VerifyOtp` is the login by an emailed or texted code, `/Account/VerifyTotp` is the fresh code).
- **New page `/Account/VerifyTotp`.** A signed-in person types the code of their authenticator app; the Server checks it (`ITwoFactorService.VerifyAsync`: a code works once, wrong codes count towards the lockout, audited as `2fa.step_up*`, rate limited with the one-time-code pages). With an allowed `ReturnUrl` the person goes on there, otherwise the page says the code was accepted. A person without two-factor gets a link to turn it on. The rule of the browser (`AccountFormRules.TotpCode`) and the texts in all seven languages are included. See [docs/ui-handover.md](docs/ui-handover.md).
- **A fresh code of the authenticator app for sensitive actions: `WithTotp()` / `[Auth2Totp]` (required) and `WithOptionalTotp()` / `[Auth2OptionalTotp]` (only people who have two-factor).** The request must carry a TOTP code (header `X-Auth2-Totp` or form field `auth2_totp`); the Client has the Server check it for the signed-in person (new route `POST /api/auth2/2fa/verify` with `code` and `optional`, `ITwoFactorService.VerifyAsync`, `IAuth2ApiClientService.VerifyTotpAsync`). A code works **once** (replay cache), wrong codes count towards the lockout, the route is rate limited and audited (`2fa.step_up`, `2fa.step_up_failed`, `2fa.step_up_replayed`). A refused request is `403` with the **error code** in the header `X-Auth2-Totp-Status` (and `{ code, message }` as the body for API calls): the new codes `totp_required` (no code) and `totp_setup_required` (the action needs two-factor and the person has none; an optional rule lets such a person pass), and `invalid_otp`, `locked_out`, `two_factor_not_allowed`, `forbidden`, `server_unavailable`. The new codes are in `Auth2ErrorCodes` and in `Errors.resx` in all seven languages. A machine token is refused; the Server is asked once per request. The MVC sample has `/Home/TotpForm`. See [docs/client-endpoint-metadata.md](docs/client-endpoint-metadata.md#ask-for-a-code-of-the-authenticator-app-totp).
- **More authorization rules for endpoints and controllers (Client).** `WithAllGroups(...)` / `[Auth2Group(true, "a", "b")]`: the user must be in **all** of the groups (roles and permissions already had the "all" form). `WithSignInMethod("swk", "hwk")` / `[Auth2SignInMethod(...)]`: the person must have signed in with one of the methods (the `amr` claim: `pwd`, `otp`, `swk`, `hwk`, `mfa`; constants in `Auth2SignInMethods`). `WithMultiFactor()` / `[Auth2MultiFactor]`: more than one factor (a verified passkey, or a password plus a one-time code). A machine token never passes the two sign-in rules. `IAuth2GroupMetadata` has a new `RequireAll` (default `false`) and there is a new `IAuth2SignInMethodMetadata`. See [docs/client-endpoint-metadata.md](docs/client-endpoint-metadata.md#the-sign-in-method-of-the-person).
- **`Clients.AutoAssignScopeToApplication`** (project setting, global admin only, default on, a checkbox in the settings page). With scope sync on: on = a pushed scope is registered and added to the allowed scopes of the application that pushed it (as before); off = it is only registered, and an admin allows it for the applications that need it, so a client can no longer allow a scope for itself. See [docs/scopes.md](docs/scopes.md#scope-sync-and-what-a-scope-really-limits).
- **The roles GlobalAdmin and Developer are protected in one place.** They can never be deleted (the role store refuses, so no code path can), no role of a project can take their names (`GlobalAdmin`, `Developer`, any letter case; the role sync skips them), and giving them to a user, taking them away, adding them to a group or removing them from one, and joining a group that has them, are allowed only for a person who holds `GlobalAdmin` or `Developer` (read from the database; `IPrivilegedActor`). Seed and job code that is not a web request stays trusted. Before this only `GlobalAdmin` was checked, and only in some routes. See [docs/access-concepts.md](docs/access-concepts.md#the-built-in-roles-globaladmin-and-developer).
- **Docs: scope sync and what a scope really limits.** With `Clients.ScopeSyncAllowed` on (the default) an application allows any custom scope for itself, so scope checks only protect when sync is off and admins assign the scopes. [docs/scopes.md](docs/scopes.md#scope-sync-and-what-a-scope-really-limits).
- **MVC sample: scope rules that fail.** `/Home/ScopeFails` (`[Auth2Scope("payments.refund")]`) and `/Home/ScopeFailsInCode` (a `HasScope` check that answers a JSON `403 insufficient_scope`) use a scope the application does not have, so you can see a refused scope. Both are on the Showcase page and in [docs/sample-mvc.md](docs/sample-mvc.md).
- **Web server address and type of an application.** The table `applications` has two new columns, `web_server_url` and `kind` (`Web`, `Api`, `Service`, `Other`; migration `ApplicationWebServerAndType`). A global admin sets them on the application page or in the admin API (`applicationType`, `webServerUrl`); a client announces them in its handshake (`Auth2ClientOptions.WebServerUrl`, `ApplicationType`; the type is worked out when not set, `PublicUrl` is the fallback address). The new application setting `AllowClientToSetWebServerUrl` (on the application page, global admin only, default on) decides whether the client may replace them; when off the handshake answer says `webServerLocked`. The two-way health check calls `{WebServerUrl}{path}` first. The seed gives the samples their types. See [docs/handshake-and-startup.md](docs/handshake-and-startup.md#the-web-server-address-and-the-application-type).
- **Worker sample** (`samples/SystemX.Auth2.Samples.Worker`): a background job that works as a program (machine to machine). It gets a machine token, calls the MinimalApi sample with it (accepted through the audience of the scope `jobs.run`) and reads the permission catalog from the Server. The seed creates its application `worker-sample`; docker-compose runs it as `sample-worker`. The README explains the configuration and how to register a job of your own.
- **Health on the home page of the console.** *Subsystem & Job Status* now shows PostgreSQL from the real health check (it was a fixed text) and a new Redis row (`Connected`, `Degraded`, `Unhealthy` or `Off`); the *Projects* card shows how many projects are `healthy`; every project under *Configured Projects* has a health badge beside `Active`. The PostgreSQL and Redis check is one service now (`IInfrastructureStatusService`), shared with the project dashboard.
- **Health badge in the list of projects** (`/admin`): beside `Active` every project shows `Healthy`, `n of m not healthy`, `Unknown` or `No health check`, from the two-way health check of its applications (`IClientHealthService.GetProjectsAsync` reads all the projects of the page at once). See [docs/client-health-check.md](docs/client-health-check.md).
- **`PublicUrl` of the two-way health check is optional.** Without it the client tells the Server only its port, scheme and path (`ClientHandshakeRequest.HealthPort`, `HealthScheme`, `HealthPath`; found in `urls`, `ASPNETCORE_URLS`, `http_ports` or the web server addresses) and the Server calls `http://{network address of the handshake}:{port}{path}`. With `PublicUrl` the Server calls exactly that. Both samples and docker-compose no longer set it.
- **Refresh buttons** next to the `Clients`, `PostgreSQL` and `Redis` badges of the project dashboard: the `Clients` one asks this project's two-way clients now (`IClientHealthService.CheckProjectAsync`).
- **PostgreSQL and Redis on the project dashboard.** The server's two health checks (`database`, `redis`) are shown to global admins as badges (`PostgreSQL: Healthy`, `Redis: Healthy` or `Redis: Off`) beside `Jobs` and `Status` on `/admin/p/{project-key}`. See [docs/observability.md](docs/observability.md#health-checks).
- **A complete guide to scopes.** `docs/scopes.md` explains the standard, `auth2.*` and custom scopes, how a scope gets into a token, how to create, allow, ask for and check one, and the resources of a scope (the page that was `scope-resources.md` is part of it now).
- **Two-way health check.** `EnableHealthCheck(o => o.Mode = Auth2HealthCheckMode.TwoWay)` (with `PublicUrl` and an optional `Path`, default `/auth2/health`): the client also answers the Server's question "are you healthy and ready?" with the result of all its health checks, the handshake tells the Server where (`ClientHandshakeRequest.HealthUrl`), and the Server asks every minute (`Auth2:Jobs:ClientHealthEnabled`, `ClientHealthIntervalSeconds`, `ClientHealthTimeoutSeconds`) and shows `Clients: Healthy` (or `n of m not healthy`) on the project dashboard (`/admin/p/{project-key}`) beside `Jobs` and `Status`. One-way stays the default. Both samples use two-way. See [docs/client-health-check.md](docs/client-health-check.md).
- **MVC sample: a showcase of every rule.** `HomeController` has one action for each kind of rule (permissions any / all / only from a role / only granted, roles, groups, scopes, scope AND permission, the "any of" family, the audit hook), a **Rules** page that lists them and an **Inspect** page that shows the checks in code and the audiences of the token. The sample scopes now have resources (`reports-api`, `orders-api`). See [docs/sample-mvc.md](docs/sample-mvc.md).
- **Scope resources are applied.** The "Associated Resources" of a scope now become audiences (`aud`) of the access tokens that have the scope (user tokens, machine tokens, and after a refresh): the client id of the application stays first, then the resources of the granted scopes. An API can accept only tokens made for it with `UseApiAuthentication(o => o.Audience = "orders-api")`. The Server finds the application of a token from the `client_id` claim (`TokenAudience`), so a resource that is another application's client id selects nothing. See [docs/scopes.md](docs/scopes.md).
- **Demo data for the samples:** when `Auth2:SeedDemoData` is `true` (default `false`; on in `appsettings.Development.json` and `docker-compose.yml`) the seeder adds demo data to `sample-project`: 60 permissions, 55 roles, 53 groups, 60 scopes (allowed for both sample applications) and 56 people (password `Demo@12345!`), with roles, groups and direct permissions assigned, so the MVC and Minimal API samples can be tried at once. The demo seed runs after the main seed is committed and cannot stop the server from starting. See [docs/seeding.md](docs/seeding.md#demo-people-for-the-samples-development-only).
- **Privacy and Terms pages** (`/Privacy`, `/Terms`): public pages with English text for an open-source, self-hosted server (data kept, cookies, recipients, user choices, MIT licence, terms of use), with a note for operators. They show the project's brand name and support address when the application is known, and the footer of the sign-in layout links to them. See [docs/ui-handover.md](docs/ui-handover.md#privacy-and-terms-pages).

### Changed
- **Social login and generic OpenID Connect now use OpenIddict.Client** (`OpenIddict.Client.AspNetCore`, `.SystemNetHttp`, `.WebIntegration`) instead of a hand-written client. Registrations are built from the provider list at run time (no restart); see ADR-096 for the spike result and the findings. Behaviour changes: a specific Microsoft tenant refuses another tenant at the issuer check; Apple, Google and GitHub follow the library (RFC 9207 `iss`); the Facebook Graph version is applied to the library's endpoints. Upstream tokens are never stored in the Server's token table.
- The HTTP clients of OpenIddict.Client get the SSRF guard (`SsrfGuardHandler`). The answer of a provider (`/callback/login/...`) is read by Auth2 itself; the OpenIddict middleware does not handle it.

### Changed (breaking, pre-1.0)
- **Project vs Application.** The old "application" (tenant + client) is split. **Project** = the tenant (table `projects`, `ProjectKey` never changes, project settings). **Application** = a client of a project and **is** the OpenIddict application table (`applications`, custom OpenIddict entities with `ProjectId`, `IsEnabled`, `Name` unique inside the project, `SettingsJson`), created, changed and deleted only through `IOpenIddictApplicationManager`.
  `user_applications` is now `user_projects`; every tenant table uses `ProjectId` (the query filter too). Audit events, sessions and synced catalog items keep an **optional** `ApplicationId`. One data-preserving migration (`ProjectsAndApplications`, hand-written, upgrade test compares the result with a fresh schema). OpenIddict major upgrades need a migration review.
  Access rule: a member of a project can use every application of it. Joining is a project setting.
  Enabled/disabled: one shared gate (`AccessGate`) for every sign-in path and token (OpenIddict event handlers for validation); generic public answer `access_denied`, the reason only in the audit log; disabling a project revokes tokens, authorizations and sessions in one transaction; a short cached status (`Auth2:ProjectStatusCacheSeconds`).
  `ServerWithSingleApplication()` is now `ServerWithSingleProject()`, `IApplicationContext` is `IProjectContext`, new `IClientApplicationContext`; claims are `project_id`, `projectkey`, `client_id`, `application_id` (the `app` claim is gone); the login cookie is per project (`.SystemX.Auth2.Session.{projectkey}`).
  Two-level settings with one resolver (`EffectiveSettings`): project default, overridden by the application value. Handshake request: `ProjectKey` (multi mode only) + `ApplicationName`; the answer returns `ProjectId` and `ApplicationId`; a key sent to a single-project server is ignored with a warning.
  Admin API: `/projects`, `/projects/{projectId}/users|roles|permissions|groups|settings|audit-events|external-*`, `/projects/{projectId}/applications/{applicationId}/...` (client setup page data, secret shown once). Commands: `create-project`, `create-application`, `rotate-client-secret <clientId>`.
- **`ICurrentClient` and `ICurrentUser` are split.** `ICurrentClient`: token, client id, application id, project id and key, scopes, `HasScope`, machine flag, session id, `Idp`, `Amr` (synchronous, from claims). `ICurrentUser`: the person only (`IsAuthenticated` is false for machine tokens).
- **Catalog sources.** One generic `CatalogOptions<T>` for permissions, roles, scopes and groups with `Add`, `AddFromClass`, `AddFromEnum`, `AddFromString`, `AddFromListString`, `AddProvider`, `AddFactory`, `AddFromConfiguration`; merge by key, `DuplicatePolicy`, startup validation that names the source; `[Auth2Key]`, `[Auth2Category]`, attributes usable on fields.
